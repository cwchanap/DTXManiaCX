# HPA-800 — Split PerformanceStage into a session owner and two playfields (design)

**Linear:** https://linear.app/cwchanap/issue/HPA-800  
**Baseline:** main `241d78d8ed040a3d7d69f01562462b5ad57ad7ab`, 2026-11-19; HPA-799 merged as PR #250.  
**Delivery:** Design-only draft PR. Implement on **this same branch/PR**; one ticket = one PR, hard target <=3 engineer days.  
**Goal:** No change to gameplay, rendered pixels, audio timing, scoring, MIDI input, controls, skin selection, or stage transitions.

## Why this split, and what is actually on main

`DTXMania.Game/Lib/Stage/PerformanceStage.cs` is 3,110 lines. It combines:
- Activation/input/pause/transitions/completion (`OnActivate` / `OnUpdate` / `OnDraw`, `FinalizePerformance`).
- Chart/notation parsing, background audio preparation, chart-first publication and late audio binding (`StartGameplayInitialization`, `PrepareGameplayCore`, `ApplyParsedChart`, `ApplyPreparedAudio`).
- Runtime audio transport and scheduled BGM events (`BindPreparedAudio`, `ProcessBGMEvents`, active SoundEffectInstance cleanup).
- Lane-specific rendering, notes, pads, judgement line, hit effects and HUD; Tab notation strip + Tab HUD; duplicate mode branching in the base, overlay, HUD, input feedback and judgement paths.
- Shared judgement/scoring/gauge/skill managers, autoplay, and timing logic.

Important existing contracts:
- **HPA-799 is already the async primitive.** `BaseStage.BackgroundWork` creates one scope per activation and applies chart, progress and audio callbacks on the update thread; queued/stale owned audio is dropped and disposed. Reuse it. Do not add a second queue, scheduler, generation counter, or Game API work queue.
- **Chart-first presentation is intentional.** Worker publishes `ParsedChart` and an optional pure `NotationChart` *before* expensive audio preparation, so a Tab strip may draw behind LOADING. The prepared audio is later bound on the update thread. Preserve this two-phase ordering.
- **One logical song clock, two uses.** Raw `SongTimer` logical milliseconds drive BGM, BGA, autoplay, visuals, and song completion; latency-compensated logical milliseconds drive only manual judgement/miss detection and nearest-note chip lookup. Freeze playback speed/pitch and autoplay lanes once per activation.
- **Tab readiness is atomic.** Requested Tab mode is not the effective mode. Both `NotationStripRenderer` and `TabHudDisplay` must be ready; failure falls back to a complete Lanes layout for the song. No strip/HUD hybrid.
- **The stage owns SpriteBatch pass boundaries.** Base alpha, overlay alpha, UI alpha and additive-effects passes have precise depth/order. The chart video is behind the opaque Tab strip and the Lanes effects do not draw in Tab.
- `PerformanceStageDeterministicTests.cs` currently has approximately 8,438 lines / 287 facts with heavy private-field reflection. This is a test-maintenance problem, not a compatibility contract. HPA-797 already provides out-of-process E2E journeys and a seven-stage CX Neon screenshot tour.

## Decision 1 — One session owner, no new infrastructure

Extract a small internal `GameplaySession` (name may be adjusted to `GameplaySessionLoader` if it remains a single stateful owner), with responsibility for:
- Snapshotting immutable inputs from `SongPlayRequest` and the frozen run configuration *before* submitting a worker to the existing `StageBackgroundWorkScope`.
- Fallback DTX parsing, pure Tab notation construction, and `PreparedGameplayAudioSet` preparation, using existing `DTXChartParser`, `NotationChartBuilder` and audio-variant services.
- Publishing the prepared chart first; binding audio later on the update thread with explicit ownership transfer and failure handling.
- Holding active chart/`ChartManager`, `AudioLoader`, prepared sounds, `SongTimer`, chip-sound cache, sorted BGM events and live BGM instances. Advancing/cleaning BGM playback from the raw logical time; stopping and disposing audio once per activation.

Keep the existing `StageBackgroundWorkScope` semantics: Latest progress, FIFO chart-before-audio callbacks, stale results disposed with `onDropped`, no worker access to a changing stage or GPU. The session reports chart-ready/audio-ready/failure to the stage through narrow callbacks. The stage remains responsible for telling gameplay managers and the playfield that a chart is published.

Preserve the silent-clock fallback, per-WAV volume/pan, non-default playback modifiers, replay/stop behavior, metronome behavior, and exact BGM due-event ordering across skipped frames. Do **not** change the chart parser, `SongTimer`, `PreparedGameplayAudioSet` internals, or BGM scheduling semantics while moving them. Background video event scheduling may remain in the stage for this PR, since no behavior change is requested.

Use direct constructor dependencies (existing services/factories); no new DI container, service registry, async abstraction, or generic event bus.

## Decision 2 — One thin playfield interface, two implementations

Add internal `IPerformancePlayfield`, implemented by `LanesPlayfield` and `TabPlayfield` under `Lib/Stage/Performance/`.

**Responsibilities:** own mode-specific rendering resources and HUD composition; update visual effects; receive immediate lane-hit and judged-hit feedback; render **within** the existing four stage-owned SpriteBatch passes. Keep only the minimum methods needed by current callers: update, base/overlay/HUD/additive draws, lane-hit/judgement notifications, dispose, and effective mode. Do not introduce an abstract base class or generalized rendering pipeline.

- **Lanes:** consolidate the present lane background/measure lines/notes/pads/judgement line, Lanes popups/effects, score/combo/gauge/skill presentation and related skin assets without changing draw order.
- **Tab:** consolidate `NotationStripRenderer`, `TabHudDisplay` and `TabModeArt`, Tab popup/key-flash handling, and Tab HUD composition. Its constructor/`TryCreate` is all-or-nothing: if either renderer or HUD cannot initialize, dispose/release partial resources and keep the existing Lanes instance.
- **Stage:** choose effective playfield once when the chart is published. Initialize a Lanes instance during activation so loading/countdown pad feedback remains immediate. On successful Tab construction, replace it without a mixed draw state. On failure, continue Lanes for that run. Do not use both playfields to render simultaneously.
- **Shared model:** scoring, judgement, gauge, autoplay, skill computation, sound timing, and a single sampled logical clock remain shared; never duplicate them per playfield. Provide a small read-only frame/feedback context from current managers and display state rather than copying business rules into views. Stage retains input routing, pause, failure/completion and Result transition.

**Boundary rule:** the stage must not check `_notationStrip == null` / `IsTabHudActive` to decide how to draw or spawn feedback; it invokes the active playfield. Only the one-time requested-style selection knows about Lanes versus Tab. Later HPA-724/HPA-773 should modify `TabPlayfield` and its components without changing `PerformanceStage`.

Do not alter `PerformanceUILayout` geometry, color, depth, Draw Begin/End count, skin texture lookup, pixel ownership, or notes' timing and visibility. Shared white-pixel `ITexture` remains reference-counted; borrowing renderers must dispose **before** the session/stage releases the owner. No new assets or SFX.

## Decision 3 — Rework tests around behavior, not private fields

Replace implementation-coupled `PerformanceStage` tests with constructor-created session/playfield tests and a small stage orchestration suite. Reuse existing mock `IStageGame`, in-memory chart/audio fakes, `StageBackgroundWorkScope` fixtures, and the E2E game API. Remove redundant reflection-only tests instead of preserving private fields, compatibility adapters or dozens of private getters **solely** for tests. Preserve unique regression coverage while retiring duplicates.

Required focused scenarios:
1. Session chart-first publication, audio-ready second, progress, cancellation/deactivation/re-entry, disposal exactly once, silent clock, prepared audio binding failure and scroll-speed changes during loading.
2. BGM events before/at/after boundaries, simultaneous events/hitches, WAV volume/pan, instance retirement, stop and replay; frozen speed/pitch and one logical clock.
3. Lanes default, Tab success, Tab missing font/HUD fallback, loading-time pad feedback, key flashes, partial-auto versus manual judgements, no Lanes effects in Tab.
4. Input/autoplay/judgement compensation, scoring, gauge, fail/clear Result payload, timer pause/resume, no duplicate subscriptions, repeated activation and cleanup.
5. Draw pass order and resource lifetime using constructor-injected fakes; avoid GPU-dependent unit assertions where a real screenshot/E2E assertion is more meaningful.

It is acceptable to remove stale tests asserting now-deleted implementation details; not acceptable to drop unique observable-behavior coverage. All surviving/new **PerformanceStage-specific** tests should construct real objects/fakes rather than `GetUninitializedObject` or private-field reflection. Do not rewrite reflection tests in unrelated stages.

## Non-goals

No scoring or note-timing changes; no new UI layout; no Tab BPM panel/hit-effect feature (HPA-773/HPA-724); no input stack/config/song library refactors (HPA-804/803/801/802); no NX compatibility code; no additional services or abstraction hierarchy; no new screenshot-diff framework.

## End-to-end acceptance contract

**Automated** acceptance, executed by an MCP-controlled game journey on **one** supported platform (Mac or Windows is enough for this platform-neutral refactor):
- Clean CX Neon launch -> SongSelect -> Lanes autoplay -> Result -> SongSelect -> Tab autoplay -> Result, with pause/resume, physical/injected hit and replay/return where automation supports them. Check game API stage/score/notes/progress results; failure and premature transition are regressions.
- Run a prepared chart featuring BGM events, overlapping or simultaneous notes, and Tab notation. Verify BGM and gameplay event timing through observable telemetry/logs and deterministic tests; a silent fallback does not prove acoustic output.
- Capture fresh 1280x720 **Lanes and Tab gameplay screenshots** via MCP. Compare visually with main's HPA-797 tour artifacts (and compare Result if changed) for layout, clipping, layer order, missing art, text, hit feedback and BGA-over-strip occlusion. No mockup exists because this is a behavior-preserving refactor.
- Unit tests pass for session, playfields, stage orchestration and existing gameplay regressions; full canonical unit suite passes; platform game build passes. Preserve existing E2E screenshot tour. Do not count skipped graphics-device unit tests as visual acceptance.
- Code review confirms no duplicated playfield mode branches in the stage, no new async queue, no legacy test compatibility fields, no change to judgement/score formulas, and proper resource ownership.
