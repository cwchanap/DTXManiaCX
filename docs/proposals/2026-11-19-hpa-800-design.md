# HPA-800 — PerformanceStage session, rules, and playfield split (reviewed design)

**Linear:** https://linear.app/cwchanap/issue/HPA-800  
**Review:** https://github.com/cwchanap/DTXManiaCX/pull/251#pullrequestreview-5987239671  
**Baseline:** main `241d78d8ed040a3d7d69f01562462b5ad57ad7ab` (HPA-799 merged as PR #250), checked 2026-11-19.  
**Delivery:** Plan-only draft PR; implementation and tests stay on **this same PR**, <=3 engineer days. No new assets, SFX, visual or gameplay features.

## Verified starting point and invariants

`PerformanceStage.cs` is ~3,110 lines. It mixes stage orchestration; chart/notation/audio preparation; BGM/chip transport; shared judgement, scoring, autoplay, completion and skill rules; and Lanes/Tab rendering.

- **Reuse HPA-799.** `BaseStage.BackgroundWork` owns the per-activation `StageBackgroundWorkScope` and update-thread `Post`/`Latest`/`Run` callbacks. The worker publishes parsed chart + pure notation *before* audio is prepared, making the right playfield visible under LOADING; stale prepared audio is dropped/disposed. No second background queue, lifecycle tokens, or worker mutation of stage/GPU state.
- **Preserve clocks and ordering.** Raw `SongTimer` logical time drives BGM/BGA/autoplay/visuals/progress/completion. Only manual judgement, miss scanning and nearest-note chip lookup use the speed-adjusted output-latency compensation. Freeze speed/pitch/automated lanes on activation. Do not reorder the stage's timer updates, input handling or event callbacks when extracting.
- **Keep one active visual mode.** Tab is effective only when both `NotationStripRenderer` and `TabHudDisplay` are ready; otherwise the whole song renders Lanes. Retain loading-time pad feedback and full four-pass `SpriteBatch` Begin/End + depth order (background video stays behind notation).
- **No pause/replay feature exists.** `InputCommandType` has no Pause and the current `_isPaused` flag is never set true. Retain Back-to-SongSelect/stop behavior, but do not add pause/resume or Result replay to this refactor.
- **Existing regression infrastructure:** HPA-797's `Category=E2E` tests drive the game over JSON-RPC and capture `05-lanes-performance.png` and `07-tab-performance.png`. `PerformanceStageDeterministicTests.cs` has ~8,438 lines and hundreds of brittle private-field/reflection calls. Prefer behavior tests over preserving their private seams.

## Decision A — Concrete `GameplayAudioSession`: preparation and audio transport only

One GPU-independent, concrete internal class under `Lib/Stage/Performance/`. It owns the worker-local `Prepare` chain, prepared audio ownership, `AudioLoader`, `SongTimer`, chip-sound cache, sorted BGM queue/active instances, and metronome. Suggested narrow operations: `Prepare` (pure/static with snapshot arguments), `Bind(chart, preparedSet)`, `Start`, `Advance(rawMs)`, `PlayChip(note)`, `StopAll`, and `Dispose`. Derive exact signatures from existing calling sites; no new interface.

The **stage owns** `BackgroundWork` scheduling, chart/progress/error callbacks, its loading/ready flags and stage transitions; the session owns audio set binding/transport and drops once. Snapshot chart/path, logger, frozen playback profile and worker dependency factories **before** `Run`. The stage publishes chart first to the rules/playfield, then binds audio later on the update thread. Maintain current failure ordering, ownership transfer and `onDropped` disposal; no audio objects or GPU initialization on the worker.

**`ChartManager` belongs to GameplayRules**, not the audio session: the rules need it on every gameplay frame. Keep BGA/video event scheduling in the stage for this PR. Preserve silent `SongTimer` fallback, pitch/speed, BGM due-event order even after frame hitches, WAV volume/pan and immediate stop on Back/completion. Reuse existing audio classes; do not change parsing or recording systems.

## Decision B — Concrete GPU-free `GameplayRules`: one source of truth for both modes

One internal class (no interface) owns frozen gameplay settings, `ChartManager`, `JudgementManager`, `ScoreManager`, `ComboManager`, `GaugeManager`, `SkillManager`, autoplay cursor and shared event fan-out. It handles:
- Automated note resolution and forwarding `OnAutoHit(lane)` **after the same existing judgement/event order**, followed by chip playback through the audio session. Manual-hit chip search and input feedback preserve compensated time.
- AutoAddGauge policy (auto lanes only), completion/failure checks including real-time end buffer, and `PerformanceSummary` construction; the **stage** performs the Result/Back transition.
- Raw-vs-compensated time calculation and a single shared per-frame gameplay snapshot for both playfields and stage telemetry.

**Fix Tab data coupling:** `BuildTabHudFrameState` currently reads `ScoreDisplay`, `ComboDisplay`, and `SkillPanelDisplay`; those are visual widgets and cannot be authoritative after Lanes is replaced. Promote/adapt the existing `TabHudFrameState` into **one** shared frame snapshot (e.g. `PerformanceFrameState`, not a second parallel DTO) populated from `ScoreManager.CurrentScore`, `ComboManager.CurrentCombo/MaxCombo`, `SkillManager.CurrentSkill` and `SkillManager`'s O(1) Perfect/Great/Good/Poor/Miss counters. Cross-check these against `JudgementManager.GetJudgementCount` in **unit tests**, not by scanning all chart notes five times per rendered frame. Preserve final Result/telemetry count semantics.

`SkillPanelDisplay` currently alone tracks Fast/Slow and duplicates judgement counters. Move the identical `PerformanceUILayout.HitTimingFeedback.ProjectDelta` rounded-millisecond success-hit classification into `GameplayRules` once per judgement (neutral/autoplay does not increment); remove duplicated widget counters/handler and update the Lanes panel from the shared snapshot. Both Lanes and Tab consume the same results, never each other.

## Decision C — Tiny `IPerformancePlayfield` with Lanes and Tab implementations

Create `IPerformancePlayfield`, `LanesPlayfield`, `TabPlayfield` under `Lib/Stage/Performance`. No base class, render engine or DI container. The stage retains the **four** `SpriteBatch` Begin/End passes and calls the active playfield to draw within them.

Minimal needed operations: `EffectiveMode`, `Update(dt)`, `OnLaneInput(lane)`, `OnAutoHit(lane)`, `OnJudgement(event, snapshot)`, `OnScrollSpeedChanged(percent)`, `DrawBase/DrawOverlay/DrawHud/DrawAdditive(spriteBatch, snapshot)`, `Dispose`. Do not copy scoring/timing/skill or manager ownership into these classes.

- `LanesPlayfield`: lane background/measure lines/notes, pads and judgement line, Lanes popup/effects, score/combo/gauge/skill widgets, lane flash and current scroll-speed rendering. Keep current asset resources and draw positions. Do not recalculate metrics.
- `TabPlayfield.TryCreate`: notation strip, Tab HUD/art and Tab-specific popup/key flashes. Publish **only when both strip and HUD are ready**; otherwise release partial assets and retain an intact Lanes playfield. No mixed rendering, no new hit effects/BPM widgets.
- **Stage lifecycle:** create Lanes on activation (feedback must work under LOADING), then **once on chart publication** select Tab if requested and ready; otherwise keep Lanes. Replace/dispose owned resources only at safe update-thread boundaries. Input, autoplay pad feedback, scroll-speed hotkeys, and judgement effects call the active playfield without `_notationStrip == null` / `IsTabHudActive` branches scattered through the stage.
- Provide test-friendly `protected virtual` playfield factories, following existing `CreateSpriteBatch` / `CreateChartVideoPlayer` seams; use constructor fakes to test orchestration without a GPU. Keep background/BGA, loading indicator, global toast, scene transitions and telemetry in the stage.

No change to `PerformanceUILayout`, blend/depth order, visual geometry, render paths, skin selection, or default/fallback behavior. Preserve borrowed white-pixel `ITexture` lifetime: dispose visual borrowers first, then release the resource-owner reference.

## Decision D — Delete dead code rather than migrating it

Confirm production references, then delete `LoadBGMSoundsAsync` (never called), `_laneDividerTexture` / `_laneFlashTexture` (empty draw branches), `_progressFillTexture` / `_comboDigitsTexture` / `_scoreDigitsTexture` / `_judgeStringsTexture` (loaded but not drawn), and stage-only `_isPaused` / `_pauseOverlayTexture`. Remove obsolete reflection tests targeting these dead members; do **not** delete genuine `SongTimer` pause support or active danger overlays.

## Test strategy and budget

Allocate work by **moved member**, not by a separate late test sweep. After each extraction, port the unique regression tests to direct `GameplayAudioSession`, `GameplayRules`, or playfield constructors; delete repeated tests asserting old private implementation details. The old tests include hundreds of `SetPrivateField` / `GetPrivateField` / `InvokePrivateMethod` calls and cannot all be mechanically translated within 3 days. No surviving `PerformanceStage` test may require an uninitialized stage or private-field reflection; unrelated tests remain out of scope. Each step must leave `dotnet test DTXMania.Test/DTXMania.Test.csproj` fully green; failing reflection tests may not be postponed until the final step.

Test contracts: chart-first / audio-later and stale resource drop; event ordering; speed/pitch and time compensation; per-note/autoplay judgement and Fast/Slow; single-mode Tab fallback; graphics resource disposal; BGM/chip and metronome; completion/Result payload; no double subscriptions. Standalone session/rules tests should be GPU-free; stage telemetry and playfield factories provide the outer behavior tests.

## End-to-end acceptance (MCP required)

On **one supported platform**, use MCP to execute/observe the **existing, repeatable out-of-process** `Category=E2E` game runs rather than inventing a separate hand-driven click script. Reuse `GameplayFullAutoPlay_ShouldJudgeEveryNoteAndComplete`, `GameplayTabAutoPlay_ShouldJudgeEveryNoteInEffectiveTabModeAndComplete`, `DefaultSkinFirstRunSmokeTests`, `MidiGameplaySmokeTests`, `ChartBackgroundVideoSmokeTests`, and `TabImportSmokeTests`.

- MCP records green game build/canonical unit suite and E2E runs **at the base revision and implementation head**, with stage/score/judgement/effective-Tab telemetry and game process logs; ordinary `dotnet test` output alone is not proof of an MCP-controlled acceptance run.
- MCP captures/collects `05-lanes-performance.png` and `07-tab-performance.png` from both runs at 1280x720, performs a **visual** comparison for positions, clipping, sprites, staff lines, judgement/hit feedback, BGA behind strip and correct CX Neon skin, and attaches evidence to the implementation PR. There is no UI mockup for this behavior-preserving refactor.
- Tab resource failure uses deterministic injected-factory tests to prove full-Lanes fallback; no destructive skin manipulation needed in production E2E. Test Back-to-SongSelect and Result completion, not nonexistent pause/replay behavior.
- Cross-platform artifacts may be built but one native platform is sufficient absent platform-specific changes. Do not claim a silent-clock fallback proves audible output. Skipped graphics unit tests never substitute for screenshot inspection.
