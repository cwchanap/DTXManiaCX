# HPA-799 — Stage-scoped background work applied on the update thread (design)

**Linear:** https://linear.app/cwchanap/issue/HPA-799/architecture-one-shared-helper-for-background-work-applied-on-the  
**Planning baseline:** main at d8a0b5ef3b4555012a2861c8dd302b0fe01914d9 (2026-11-16 local time).  
**Prerequisites:** HPA-796 (including PRs #240/#241) and HPA-797 (including #237/#238) are merged.  
**Delivery:** This draft is documentation only. The implementation agent continues in **this same PR**, with a hard <=3 engineer-day budget. One ticket, one PR.

## Problem and outcome

StartupStage, SongSelectionStage, PerformanceStage and ConfigStage independently arrange background work and protect the resulting stage-owned state with activation counters, locking or per-stage completion queues. The stages can be reactivated on the same cached instance. Late callbacks must never mutate a departed activation, and successful callbacks must run on MonoGame's update thread.

Introduce **one small, stage-scoped background-work helper**, based on BaseGame's **existing** main-thread action queue. Apply completed work/progress on the game thread, then delete the duplicated **activation** guards and per-stage completion queues whose job the helper replaces. Preserve user-visible behavior, chart/audio timing, filtering and asynchronous progress.

This is lifecycle plumbing, **not** the separate PerformanceStage/SongSelectionStage/SongManager architecture split.

## Verified code findings

- Game1.cs: BaseGame already owns a ConcurrentQueue<Action>; IGameContext.QueueMainThreadAction enqueues it. DrainMainThreadActions executes up to **64 callbacks per frame after StageManager.Update** and before Draw. Keep that queue and its ordering/limit; do not add another dispatcher, event loop or thread.
- BaseStage.cs: Activate/Deactivate own the actual cached-stage lifecycle; **OnDeactivate runs before CurrentPhase becomes Inactive**. A plain IsActive check is insufficient, especially after leave and re-entry. Invalidate pending callbacks **before** OnDeactivate.
- StartupStage.cs: BeginActivationScope / RetireActivationScope, _activationGate and _activationGeneration protect song-load continuations, progress and fallback. SongManager's underlying library processing remains independent.
- SongSelectionStage.cs: activation tags and queues guard song initialization, tab completion, bookmark rollback and library publications. There are also **genuine same-activation request versions** (bookmark toggle, latest tab/bookmark load) whose last-write-wins semantics must remain.
- PerformanceStage.cs: InitializeGameplayCoreAsync can resume on a worker, writes loading/chart/audio/notation fields and uses _activationGeneration and AudioLifecycleGate around publication/teardown. PreparedGameplayAudioSet is disposable; a completed-but-stale result **must be disposed** without binding sounds.
- ConfigStage.cs: asynchronous reload/NX import posts status through _songOperationUpdates and _activationGeneration. ConfigSongOperationLease handles per-operation ownership; keep that semantics.

## Design decisions

### A. Reuse the game queue via one explicit stage seam

- Add a narrowly named queue/post method to IStageGame; BaseGame forwards it to **the exact queue** already used by IGameContext. Keep the 64-per-frame drain and after-stage-update placement. Adjust the existing exception log label so it no longer calls every action a Game API action.
- Introduce one internal helper, e.g. StageBackgroundWorkScope, under Lib/Stage. BaseStage creates a **new scope object per successful activation**, makes it available to derived stages, and retires/cancels it **before** OnDeactivate. BaseStage's Dispose follows that same path. Never use a global singleton, DI framework, generic job broker or separate queue.
- Each worker captures its scope object and cancellation token. Its success, progress and error UI callbacks are posted to the existing queue, then **rechecked on the update thread** against that scope's live state before applying. The identity of the captured scope prevents an old activation from applying after re-entry without per-stage generation integers. A queued action is allowed to execute after leaving, but it must be a no-op for stage state.
- Provide only the minimal helper operations needed by the four call sites: run/observe a background task and post a guarded callback (including progress); allow an optional dropped-result disposal callback for owned resources. Errors and cancellation must always be observed; log real current-activation failures once. Do not use async void, synchronous task waits on Update, unbounded per-frame drains, or a new task scheduler. Cancellation is best effort; never block Deactivate waiting for a worker.
- Preserve the worker/update ownership split: parsing, database queries and audio file preparation can run on workers; MonoGame resource creation, UI state mutations, binding prepared audio, renderer construction and stage transition requests run on the update thread. Do not move blocking I/O onto the game loop.

### B. Adopt the scope at existing, narrow boundaries

1. **StartupStage:** Retain song enumeration/cache/fallback decisions and progress messages, but route any stage-state or UI change after an asynchronous continuation through scope-guarded main-thread publication. Retain cancellation of in-flight work; delete _activationGeneration and _activationGate only after the guarded paths no longer require them. Keep SongManager library threading and its public events unchanged.
2. **SongSelectionStage:** Replace stage-activation-tagged initializer, tab-load, bookmark-revert and library-notification completion queues with guarded posts. Reconcile **the newest coherent library snapshot** on the update thread; never apply an older snapshot over a newer publication. Maintain bookmark persistence ordering and its per-song toggle version, and latest-request-wins checks for tab/bookmark loads. A committed bookmark DB write may outlive the stage; cancel/drop its **UI rollback**, not silently discard the persistence task. Remove the activation-only counters/queue gates.
3. **ConfigStage:** Route reload/import progress and terminal status onto the update thread through the scope. Preserve the operation lease, cancellation and mutual exclusion between operations; a stale progress event must not replace the current operation's final status. Remove _songOperationUpdates and its activation generation, not the domain operation ownership.
4. **PerformanceStage:** Prepare/parse on workers into a local result, then publish stage-owned managers, notated chart, audio bindings, readiness/failure and GPU-dependent resources on the update thread. Respect existing prepared-chart reuse, Lanes fallback, audio clock, BGM order and cancellation behavior. Dispose PreparedGameplayAudioSet if the scope has retired or publication fails; never bind/dispose it concurrently with teardown. Once publication and cleanup are serialized on the update thread, remove the now-redundant activation generation/pending notation hand-off and **only** AudioLifecycleGate usage proven redundant. Leave other audio-internal synchronization alone.

**Crucial distinction:** remove lifecycle generation counters that duplicate the new scope. Retain **domain request/operation ordering identifiers** where two requests can legitimately race *within the same activation*. Do not add a generic latest-job-wins engine just to eliminate those numbers.

### C. Tests and failure contracts

- Unit-test the helper with a controllable fake update queue: completion posts but does not apply before drain; success applies exactly once on the draining thread; retiring a scope drops queued and late completions; reactivation cannot revive prior callbacks; errors/cancellation are observed; disposable stale results are disposed; a worker that ignores cancellation does not block Deactivate. Verify the existing 64-action budget remains intact.
- Extend existing affected stage tests rather than creating a second harness. Test direct leave/re-enter after song load, two overlapping bookmark/tab loads, library publication ordering, Config operation replacement, failed/cancelled imports and Performance parse/audio success/failure/cancellation. Preserve no-audio fallback and Tab/Lanes switching.
- Screenshot and behavior verification use the existing **bundled CX Neon** HPA-797 seven-stage tour. No HPA-799 UI mockup is attached to Linear; compare actual before/after screenshots of stable regions and flag clipping, missing content or unintended geometry changes. Dynamic notes/timers may differ, so don't require whole-frame pixel identity.

## Boundaries and risks

- **Out of scope:** HPA-800 playfields/session-loader extraction, HPA-801 SongManager/DB split, HPA-802 SongSelection component split, HPA-803 config registry, new art/SFX, UI changes, database schema changes, new compatibility shims, platform-specific scheduler or dependency injection overhaul.
- **Highest risk:** old audio-preparation result binds after Performance teardown, leaking or disposing a live sound. The helper's disposal-on-drop contract plus update-thread publication protects this.
- **Other risks:** stale library snapshots superseding newer ones, canceled bookmark persistence losing user intent, progress arriving after a terminal status, and queue work affecting frame time. Keep domain ordering checks, apply only lightweight state on the game thread, and retain the existing 64-callback limit.
- Do not claim all locks are removable: retain locks protecting genuinely shared non-stage state and active audio ownership until proven redundant.

## End-to-end acceptance (implementation PR)

- The four stages use the **same** stage-scoped work helper; no stage-specific **activation** generation counter or completion queue remains for work migrated into it. Same-activation request versions remain only where required for correctness. Main-thread callbacks use BaseGame's existing capped queue.
- Deterministic tests prove leave -> complete old work -> re-enter, leave -> re-enter -> old callback, overlapping same-activation requests, current/canceled faults, and cleanup of discarded owned audio. No worker mutates stage-owned presentation or MonoGame graphics/audio-binding objects.
- On at least **one platform**, an agent runs a **live MCP-driven** journey: Startup -> Title -> SongSelect; leave/re-enter SongSelect during a slow load; Config -> start reload or import -> leave/re-enter; Lanes gameplay -> Result -> SongSelect; Tab gameplay -> Result; repeat a Performance activation while the previous initialization is still in flight. Use supported MCP state/input tools plus deterministic fixtures/injected test delays where needed. Assert stage readiness, no stale updates/leaks/errors and retained chart/audio/result behavior. Existing xUnit E2E smoke also passes.
- Capture before/after **CX Neon screenshots** (reuse the HPA-797 tour/test screenshot infrastructure) for Title, Config, SongSelect, Lanes, Tab and Result. Compare stable visual regions programmatically / by agent visual inspection; no UI mockup exists for this behavior-preserving task. Verify no new clipping, missing UI, altered placement or wrong stage.
- Build Windows and macOS game projects and run the canonical DTXMania.Test unit suite; one platform's **MCP E2E** is sufficient because the change has no platform-specific code. Attach actual commands, screenshots, observed results, and unverified cases to this **same PR**. No human sign-off criterion.
