# HPA-799 — Stage-scoped background work applied on the update thread (design)

**Linear:** https://linear.app/cwchanap/issue/HPA-799/architecture-one-shared-helper-for-background-work-applied-on-the  
**Planning baseline:** main at d8a0b5ef3b4555012a2861c8dd302b0fe01914d9 (2026-11-16 local time).  
**Prerequisites:** HPA-796 (including PRs #240/#241) and HPA-797 (including #237/#238) are merged.  
**Delivery:** This draft is documentation only. The implementation agent continues in **this same PR**, with a hard <=3 engineer-day budget. One ticket, one PR.

## Problem and outcome

StartupStage, SongSelectionStage, PerformanceStage and ConfigStage independently arrange background work and protect the resulting stage-owned state with activation counters, locking or per-stage completion queues. The stages can be reactivated on the same cached instance. Late callbacks must never mutate a departed activation, and successful callbacks must run on MonoGame's update thread.

Introduce **one small, stage-scoped background-work helper** with a queue drained at the start of `BaseStage.Update`, before stage input. This deliberately does **not** reuse BaseGame's Game API queue: its drain happens after `StageManager.Update` and would change the stages' current apply-before-input behavior. Coalesce high-volume progress (latest only), remove duplicate **activation** guards/queues, and preserve chart/audio timing, library ordering and player-visible behavior.

This is lifecycle plumbing, **not** the separate PerformanceStage/SongSelectionStage/SongManager architecture split.

## Verified code findings

- Game1.cs: BaseGame already owns a Game API ConcurrentQueue<Action> capped at **64 callbacks per frame**, but it drains **after** StageManager.Update. Migrating stage results there would delay their availability until after the stage handles input, and reflection-built BaseGame tests do not reliably initialize that queue. **Leave the Game API queue alone**; the new stage scope has its own bounded queue, drained before the stage's OnUpdate. Do not modify IStageGame or Game1.
- BaseStage.cs: Activate/Deactivate own the actual cached-stage lifecycle; **OnDeactivate runs before CurrentPhase becomes Inactive**. A plain IsActive check is insufficient, especially after leave and re-entry. Invalidate pending callbacks **before** OnDeactivate.
- StartupStage.cs: BeginActivationScope / RetireActivationScope, _activationGate and _activationGeneration protect song-load continuations, progress and fallback. SongManager's underlying library processing remains independent.
- SongSelectionStage.cs: activation tags and queues guard song initialization, tab completion, bookmark rollback and library publications. There are also **genuine same-activation request versions** (bookmark toggle, latest tab/bookmark load) whose last-write-wins semantics must remain.
- PerformanceStage.cs: InitializeGameplayCoreAsync can resume on a worker, writes loading/chart/audio/notation fields and uses _activationGeneration and AudioLifecycleGate around publication/teardown. PreparedGameplayAudioSet is disposable; a completed-but-stale result **must be disposed** without binding sounds.
- ConfigStage.cs: asynchronous reload/NX import posts status through _songOperationUpdates and _activationGeneration. ConfigSongOperationLease handles per-operation ownership; keep that semantics.
- Config/SongFolderPanel.cs: the folder picker independently uses _activationGeneration and _pickerCompletions. It can close/reopen **without leaving ConfigStage**, so keep its per-picker CTS identity to reject an obsolete selection even inside the same stage activation.

## Design decisions

### A. One stage-local scope; apply before input

- Add one internal StageBackgroundWorkScope under Lib/Stage. A successful BaseStage.Activate creates a **new scope per activation**; BaseStage.Deactivate retires it **before** OnDeactivate; BaseStage.Dispose uses the same retirement path. Its private ConcurrentQueue<Action> is drained at the beginning of BaseStage.Update, **before** OnFirstUpdate/OnUpdate. Do not touch IStageGame, BaseGame, its Game API queue or its unrelated 64-action budget.
- Keep a small **per-stage drain budget (up to 64 callbacks per frame)**, without allowing long-running operations on the update thread. This is a stage-activation queue, not a new thread, event loop or scheduling system. Tests drive the real drain with stage.Update.
- A worker captures the scope and token; it never writes mutable stage-owned/UI/audio-binding state. In multi-step work, **all intermediate decisions stay in worker locals** (for example Startup's _cacheLoadPathSelected fallback choice must become a local), and the chain publishes **one terminal result**, plus coalesced progress. Performance's ChartManager, InitializeGameplayManagers, sounds/timer/metronome and ready flags are created/applied on the update thread rather than on its ParseAsync/PrepareAsync continuation.
- Minimal operations (names illustrative): Token, Post(Action), Latest<T>(Action<T>) producing an IProgress<T> whose **newest value replaces older undrained progress and consumes at most one queued callback per reporter**, Run<T>(work, onSuccess, onError, optional onDropped), Drain and Retire. Result success/error callbacks are FIFO; **do not coalesce terminal results**. A guarded callback checks its captured scope is still live when applied; old scopes cannot become live again on re-entry.
- Retire cancels work **without waiting**, prevents further stage mutation, and drops already-queued results. For owned data such as PreparedGameplayAudioSet, call onDropped **exactly once** whether a result was queued before leave or completed later. Observe all worker exceptions; treat expected cancellation as non-error. Never use async void, synchronous waits on Update, or an unobserved Task.
- A scope-owned CancellationTokenSource with **no linked tokens, timers or WaitHandle** may be canceled and left undisposed to avoid races/continuation scaffolding; if future work adds handles, re-evaluate. This does **not** remove disposal for per-operation CTS, leases, or owned audio. Catch terminal errors once in Run; its fire-and-forget outer task should not fault. Guard against exceptions from callbacks/cleanup without masking the primary failure.
- Latest progress must not overwrite a completed operation's terminal status: keep the existing operation lease / request identity and reject progress that arrives after the terminal callback. The UI reacts to only the latest value at drain; terminal completion remains guaranteed and correctly ordered.
- Workers perform parsing, database queries, file I/O, and sound preparation. Update-thread callbacks own UI/MonoGame resources, playback binding, active-stage state and transitions. SongManager's independent background library service remains unchanged.

### B. Adopt the scope at existing, narrow boundaries

1. **StartupStage:** Keep song enumeration/cache/fallback control flow and progress, but move worker-dependent cache/need-enumeration flags into **local chain state**, then publish one terminal result to the stage scope plus `Latest` progress. Do not post an intermediate value the worker will need again. Retain cancellation; delete the duplicate activation gate/generation and task-observation boilerplate only once the new scope protects all migrated paths. SongManager threading/events stay unchanged.
2. **SongSelectionStage:** Replace activation-tagged initializer, tab-load and bookmark-rollback completion queues with scope-guarded callbacks. Use `Latest` for library publication notifications, then reconcile the **newest coherent snapshot** on the update thread; never overwrite it with an older initializer result. Retain per-song bookmark persistence ordering, toggle versions, tab/bookmark latest-request wins and the tab-refresh version. A DB write may outlive the stage; drop only its stale **UI rollback**, not the persistence task. Remove activation-only counters/queue gates.
3. **ConfigStage + SongFolderPanel:** Route reload/import status via coalesced `Latest` progress and a distinct FIFO terminal `Post` guarded by the Config operation lease. Delete Config's activation generation/completion queue, **not** the lease or per-operation CTS. Pass the Config scope to SongFolderPanel for picker completions; remove its activation generation and picker queue, but keep `IsActive` plus the captured picker CTS identity so a completion from an earlier **open/close within one Config activation** cannot apply. Ensure picker CTS is disposed on both delivered and dropped paths.
4. **PerformanceStage:** Return parsed chart and prepared audio from the worker; publish ChartManager, gameplay managers, notation staging/construction, audio bindings, timer, metronome, readiness/error and any GPU-dependent resources on the update thread. Use `Latest` for audio-preparation progress. Respect prepared-chart reuse, Lanes fallback, audio clock, BGM order and cancellation behavior. `onDropped` disposes PreparedGameplayAudioSet on stale/failed publication exactly once. After update-thread serialization, remove duplicate activation generation/pending notation queue, CTS/observation scaffolding and **only** AudioLifecycleGate usages proven redundant; retain independent audio synchronization.

**Crucial distinction:** remove lifecycle generation counters that duplicate the new scope. Retain **domain request/operation ordering identifiers** where two requests can legitimately race *within the same activation*. Do not add a generic latest-job-wins engine just to eliminate those numbers.

### C. Tests and failure contracts

- Unit-test the helper through a real BaseStage.Update drain (or internal Drain seam only when necessary): queued completion applies **before** stage input, at most once, only for the same scope; re-entry cannot revive old callbacks; retire drops both queued-before-retire and completed-after-retire owned results exactly once. Prove `Latest` coalesces 10k reports to one pending apply, terminal results cannot be starved/overwritten, expected cancellation/fault handling and non-blocking Deactivate. Cap a stage drain to 64 callbacks per frame while leaving the Game API queue unchanged.
- Extend existing affected stage and SongFolderPanel tests; budget ~60 reflection references in StartupStageLogicTests, SongSelectionStageTabTests, SongSelectionPublicationTests, SongSelectionStageBookmarkToggleTests, PerformanceStageDeterministicTests and ConfigStageLogicTests. Pure logic tests on reflection-built objects need no scope; tests exercising async/apply should construct/Activate the stage (or install a minimal internal test scope) and drive stage.Update. Avoid production lazy activation solely for GetUninitializedObject tests. Cover same-activation picker reopen, tab/bookmark overlap, coherent library publication, Config lease/status ordering, and Performance audio fallback.
- Visual verification reuses the existing **bundled CX Neon HPA-797 seven-stage tour screenshots**, checked by an agent for missing content, clipping and wrong-stage captures. HPA-799 has no UI mockup. **No new before/after pixel/region diff gate** for a refactor that changes no drawing code.

## Boundaries and risks

- **Out of scope:** HPA-800 playfields/session-loader extraction, HPA-801 SongManager/DB split, HPA-802 SongSelection component split, HPA-803 config registry, new art/SFX, UI changes, database schema changes, new compatibility shims, platform-specific scheduler or dependency injection overhaul.
- **Highest risk:** old audio-preparation result binds after Performance teardown, leaking or disposing a live sound. The helper's disposal-on-drop contract plus update-thread publication protects this.
- **Other risks:** a 10k-chart scan flooding progress; stale library snapshots superseding newer ones; canceled bookmark persistence losing intent; a picker from a previous same-stage panel opening applying; and progress overwriting terminal status. Coalesce progress, retain per-operation identity/version guards, cap the stage drain, and keep IO off the update thread.
- Do not claim all locks are removable: retain locks protecting genuinely shared non-stage state and active audio ownership until proven redundant.

## End-to-end acceptance (implementation PR)

- Four stages **and Config's SongFolderPanel** use the shared scope; migrated per-stage activation counters/queues are removed, while per-operation/same-activation identity guards remain. BaseStage.Update drains the bounded **stage-local** queue before input; BaseGame's independent Game API queue remains unchanged. Progress is latest-only; terminal callbacks are never coalesced.
- Deterministic tests prove leave -> complete old work -> re-enter; queue-before-leave and late-after-leave disposal; 10k-report progress coalescing; overlapping same-activation requests, picker close/reopen, current/canceled faults, and correct Config terminal status. No worker mutates stage-owned presentation or MonoGame graphics/audio-binding objects.
- On at least **one platform**, an agent runs a **live MCP-driven** standard journey: Startup/Title -> SongSelect -> Lanes gameplay -> Result -> SongSelect -> Tab gameplay -> Result -> Config (with folder panel navigation). Assert stage readiness, no unexpected errors and chart/audio/result behavior using supported MCP tools; run the existing xUnit gameplay E2E smoke. **Do not introduce artificial production delay hooks**: forced late-completion cases are deterministic unit tests only.
- Verify the existing bundled **CX Neon seven-stage screenshots** (HPA-797 tour, including DrumConfig). Agent visually checks representative Title, Config, SongSelect, Lanes, Tab and Result for legibility, missing UI, clipping and correct stage. **No pixel diff, no new screenshot infrastructure**, and no human approval criterion.
- Build Windows and macOS game projects and run the canonical DTXMania.Test unit suite; one platform's **MCP E2E** is sufficient because the change has no platform-specific code. Record actual commands, tests and screenshots reviewed, and unverified cases on this **same PR**. No human sign-off criterion.
