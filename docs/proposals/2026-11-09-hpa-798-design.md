# HPA-798 — Canonical CX Neon System skin and documentation cleanup (design)

**Linear:** https://linear.app/cwchanap/issue/HPA-798/repo-make-cx-neon-the-system-skin-and-refresh-claudemd-and-docs  
**Status:** Design for review; **no implementation in this planning commit**.  
**Delivery:** One implementation PR using this draft branch, <=3 engineer days.  
**Reviewed:** DTXManiaCX main on 2026-11-09 (current .NET 10 / MonoGame repository).  
**Intent:** Align fresh development runs, published builds, release artifacts and agent documentation around one canonical CX Neon skin. No gameplay or skin-loader redesign.

## Verified baseline

- `System/Graphics/` is the old NX-derived artwork (~43 MB). The release workflow explicitly refuses to distribute it and currently flattens `System/CXNeon/{Graphics,Sounds,Theme.ini}` (~4.6 MB) into a separate staging directory.
- `System/Theme.ini` contains NX palette overrides; `System/CXNeon/Theme.ini` contains the actual shipped CX Neon theme. Keeping both as candidates is misleading and risks wrong dev visuals.
- `AppPaths.GetBundledSystemSkinRootCandidates` already handles `<exe>/System` for portable/dev builds and `Contents/Resources/System` for a macOS `.app`. `ConfigManager` already supports the relocatable `Default` token and preserves explicitly selected custom skins. No new runtime path resolver or app-data copy is needed.
- Neither `DTXMania.Game.Windows.csproj` nor `DTXMania.Game.Mac.csproj` currently includes repository `System/` assets in build/publish output. This is why a fresh `dotnet run` can require symlink/manual setup.
- `installer/windows/dtxmania.iss` installs the publish output recursively **and** takes a separate `SystemSkinDir`, which would duplicate the same skin if publish begins carrying it. `installer/macos/build-dmg.sh` copies published output under `Contents/MacOS` and the externally staged skin to `Contents/Resources/System`.
- Paths to `System/CXNeon` exist in the skingen default pack, sfxgen manifest, tool tests, CI/release validations, pack tests, `justfile` and tooling docs.
- `CLAUDE.md` and `AGENTS.md` are currently parallel entry points. They have stale stage/component counts and misplaced `DTXMania.Automation` / `DTXMania.VideoRecorder` documentation. `docs/superpowers/` contains historical designs, plans and evidence that no longer describe the implementation.

## Decision 1 — One source-of-truth skin tree

Canonical tracked layout after implementation:

```text
System/
  Theme.ini         # CX Neon
  Graphics/         # CX Neon generated/committed assets
  Sounds/           # CX Neon OGG assets
  README.md         # concise provenance + generator instructions, if useful
```

- Move the **existing** CX Neon assets and theme into the root. Remove the NX-derived `System/Graphics` and obsolete NX `System/Theme.ini`; remove the now-unneeded `System/CXNeon` folder. Do not regenerate artwork or audio as part of the relocation.
- Track the resulting assets only once. Verify source/artifact correspondence with generators and manifests after paths change; retain source art under `tools/skingen/source`.
- Preserve existing texture, sound and theme keys. The base skin is still named **Default** in runtime config; avoid introducing a second selectable bundled `CXNeon` copy.
- Keep per-user custom skins under the app-data System folder unchanged. The immutable app-bundled skin and per-user skins remain separate.
- **Rights boundary:** Do not ship NX/GITADORA-derived assets. Removing current tracked files is in scope; rewriting Git history is expressly out of scope.

## Decision 2 — Make normal build/publish include System

- Add MSBuild content items in both platform game project files (or a single small shared target if that proves simpler) to copy the canonical `System/Theme.ini`, `Graphics/**` and `Sounds/**` to `<output>/System` for `dotnet build`/`dotnet run` and to `<publish>/System` for `dotnet publish`.
- Use `PreserveNewest` and preserve relative paths. Make the compile/publish output deterministic without a developer symlink, mutable app-data operation or post-build shell command.
- Avoid including nested `System/CXNeon` or old `System/Graphics` assets. Keep existing bundled songs, FFmpeg and font-license items untouched.
- Existing `AppPaths`/`ConfigManager`/`SkinManager` fallback logic should work as-is. Only fix runtime code if a focused regression proves a real path issue.

## Decision 3 — Simplify packaging, with one copy per artifact

- **Windows portable/installer:** `dotnet publish` now already includes `System/`. Remove the Windows release “flatten CX Neon” staging step and its `SYSTEM_SKIN_DIR` hand-off. Remove the second Inno `[Files]` `SystemSkinDir` source and obsolete macro; the existing recursive `SourceDir` includes the skin. Retain installer `[InstallDelete] {app}\System` before upgrades so removed files never survive an install.
- **macOS development/portable:** published `System/` stays next to the executable for direct running. In `build-dmg.sh`, after copying the publish directory into `Contents/MacOS`, **move** its `System` to `Contents/Resources/System`. Update the script interface, release workflow and `test-build-dmg.sh` together. This preserves the existing macOS candidate order and avoids duplicate assets inside the `.app`.
- **CI/release:** keep image/audio integrity validation and required-asset coverage. Convert historical “pack not produced yet; skip” branches to fail-closed checks against `System/{Theme.ini,Graphics,Sounds}`. In publish/installer tests, assert the resolved skin is CX Neon and neither a nested pack nor NX assets are shipped. Keep the existing tool/installer workflow gates, without inventing a new packaging framework.

## Decision 4 — Update active references, then prune stale docs

- Retarget `tools/skingen/skingen.py` default compose/validate pack root and associated tests, `tools/sfxgen/manifest.json` output dir, `DTXMania.Test/Resources/CxNeonPackTests.cs`, workflows, `tools/README.md`, `System/README.md` and other *active* references. Review `NX_PACK_ROOT`/bootstrap behavior: do not silently read the new CX Neon tree as an NX reference.
- Remove the obsolete manual `just install-cx-neon` symlink/activation recipe; fresh development runs should not need it. Preserve other recipes.
- Update `CLAUDE.md` **and `AGENTS.md` together** to reflect the code: .NET 10/MonoGame, stage enum including DrumConfig, actual source layout and platform projects, `DTXMania.Automation`, `DTXMania.VideoRecorder` and their tests, current skin layout, accurate test commands and expected asset generation workflow. Prefer descriptions over brittle hard-coded component counts.
- Delete `docs/superpowers/` (historical implementation plans/specs/evidence) per ticket. Audit the older top-level `docs/*-implementation.md` and architecture snapshots; remove only pages whose claims are obsolete. Preserve live docs including current `docs/proposals`, useful `docs/verification`, evidence referenced by tests, active recorder docs and accurate reference material. Repair active README/tool/code links to deleted material.
- Do not replace stale documents with another sprawling documentation layer.

## Non-goals

No gameplay rendering changes, UI redesign, new theme keys, asset generation, audio change, config schema migration, manual installation flow, general refactor, installer replacement or Git-history rewrite. Do not add backward-compatibility shims for the old nested pack: no production users depend on it.

## Invariants / acceptance

1. A clean checkout with clean app-data can `dotnet run` on supported Windows and macOS and render the **CX Neon** default skin without symlinks or skin selection.
2. Build and publish output contain `System/Theme.ini`, expected `Graphics` and `Sounds`; no nested `System/CXNeon` and no stale NX assets.
3. Windows installer, Windows portable release and macOS `.app` each contain a **single** correctly located default skin. The installer still cleans up retired files on upgrade; custom app-data skins remain untouched.
4. Skingen, sfxgen, required-pack tests and workflows fail on missing/corrupt assets rather than vacuously passing.
5. `CLAUDE.md`/`AGENTS.md` and retained docs accurately reflect the repository; no active links are left pointing into deleted `docs/superpowers`.
6. All regression suites and real first-run/packaging smoke checks pass, with recorded results in the implementation PR.

## Delivery decision

**Use this draft PR for both design review and subsequent implementation.** Do not open separate PRs for asset relocation, packaging, tests or docs. Keep <=3 engineer days of scoped work, and defer unrelated cleanup.
