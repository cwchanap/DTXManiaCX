# HPA-801 — Split song library responsibilities (design)

**Linear:** https://linear.app/cwchanap/issue/HPA-801  
**Target:** one draft PR, with implementation and verification committed to **the same PR** after design review.  
**Baseline:** `main` at `5e8b47e311badceafc8942b804a255f0527f9463` (2026-11-21), after HPA-796/797/799/800.  
**Companion:** [implementation plan](../superpowers/plans/2026-11-21-hpa-801-implementation-plan.md).  
**Status:** design-only draft. No production code changed and no builds, tests, MCP runs, or screenshots were executed by this planning change.

## Problem and verified starting point

`Lib/Song/SongManager.cs` is now about 4,386 lines and still owns the singleton, initialization, discovery/import orchestration, SET.def/box.def parsing, filesystem freshness, hierarchy and snapshot publication, scores/NX import, and song queries. `Lib/Song/Entities/SongDatabaseService.cs` is about 2,385 lines and combines SQLite setup, bulk chart import/cleanup, score transactions, recent/bookmark/search queries, and scan metadata. The original ticket's older line counts are no longer current.

Relevant boundaries on current main:

- `SongManager`: snapshot/event state (roughly lines 168-359, 1510-1615); scan/import and hierarchy (607-2002); SET.def/box.def and folder metadata (2009-2598); score refresh/NX import (2603-3125); recent/bookmark/search/genre (3125-3315); filesystem freshness and watermark logic (3315-4078).
- `SongDatabaseService`: database lifecycle (114-316), batch import (316-1200), queries/score transactions/history/bookmarks (1202-1959), and enumeration metadata/cleanup (2001-2385).
- Consumers: `StartupStage`, `SongSelectionStage`, `ConfigStage`, `SongLibraryReloadService`, `ResultStage`, and `BaseGame`. Game startup presently calls `SongManager.Instance.ConfigureLogger`. Song Selection subscribes to `SongLibraryPublished` using HPA-799's activation-scoped `BackgroundWork.Latest`.
- Existing coverage includes `SongManagerBulkEnumerationTests`, `SongManagerLibrarySnapshotTests`, `SongManagerUpdateScoreTests`, `SongDatabaseServiceBulkImportTests`, `SongDatabaseServiceIdempotencyTests`, and the existing `Category=E2E` game-launch/screenshot tour.

**Goal:** move responsibilities into constructor-built, focused objects and delete the singleton, while preserving existing observable behavior, SQLite schema, file formats, timing, UI, and song counts.

## Decision A — one game-owned library, not a service locator

Create **one** game-lifetime `SongLibrary` composition owner. `BaseGame` creates it before the Startup stage first needs it and disposes it on shutdown. Expose `SongLibrary` on `IStageGame` so stages have the same instance without static access. Construct and supply collaborators explicitly; tests construct their own libraries with temporary or in-memory SQLite and fake I/O seams.

The owner's public surface stays small:

- Library state: `GetLibrarySnapshot()` / root publication events / initialization status; a coherent active-roots/hierarchy/count/version snapshot is published atomically.
- Focused collaborators: `Scanner`, `Scores`, and `Queries` (concrete classes, not a second dependency injection framework). Stages use the relevant collaborator directly. Initialize the store through the existing Startup database-path seam, not via a hidden global path.
- Only coordination that spans collaborators (e.g. the scan → bulk import → finalize → publish sequence) remains on the owner. Do **not** move all old methods behind a giant `SongLibrary` forwarding facade.

Keep `SongLibrarySnapshot`, `SongEnumerationBatch`, `SongEnumerationResult`, `SongListNode`, `SongRootPolicy`, chart parsers, and other DTOs unless the compiler exposes a genuinely obsolete member. No new event bus, repository abstraction hierarchy, DI container, or private-field compatibility adapter.

**Delete** `SongManager.Instance`, `SongManager.ResetInstanceForTesting`, and the old `SongManager` class once migrated. Migrate the singleton-serialized test collection and tests to isolated, constructor-built fixtures. No backwards-compatibility shim is needed.

## Decision B — discovery, definitions, and publication have separate owners

- **`SongLibraryScanner`**: canonical root validation, one-pass filesystem traversal and batch construction, change detection, cancellations/single-flight coordination, chart inventory, root watermarks, recoverable-error decisions, and cache freshness. It delegates file-format specifics to `SongDefinitionReader`, database storage to `SongCatalogStore`, and hierarchy building to `SongHierarchyBuilder`. Reuse `DTXChartParser` and the existing tab import converter; do not rewrite parsing.
- **`SongDefinitionReader`**: only SET.def and box.def decoding, fallback encodings, label/caption parsing, color/skin/folder metadata. It has no database or publication state.
- **`SongHierarchyBuilder`**: builds the temporary hierarchy from the scan batch or database rows, including SET grouping, BOX nesting, root-name disambiguation, score hydration, and bundled-song placement. It does not publish shared state.
- **`SongLibrary`**: owns one lock protecting the published hierarchy, active/pending root set, published counts/version and the atomic score-snapshot refresh mutation. Publishes complete states and raises existing event callbacks **outside** the lock; a throwing subscriber cannot break later subscribers.

Preserve these non-obvious contracts exactly:

1. A competing scan throws `SongEnumerationBusyException`; cancellation does **not** release the occupied scan slot until its task ends. A canceled/failed scan must not publish partial nodes.
2. The DB bulk import commits before pending nodes are finalized and the completed hierarchy is published. Preserve post-commit failure reporting rather than reporting a successful publication on finalize failure.
3. The freshness watermark is based on *scan start* (with the existing 5-second backoff), persisted only for successfully scanned roots; recoverable parse/read failures remain dirty. Rejected chart counts, active-root scoping, missing/moved file detection, and retained rows for inactive roots must behave as before.
4. Empty-root acceptance publishes an explicit empty snapshot. Unavailable/incomplete roots must not erase an already valid published hierarchy.
5. Configured roots plus bundled songs are combined once, retaining the current bundled-root top-level merge behavior and no unexpected duplicate root boxes.
6. Stage publication event handlers remain activation-scoped and coalesced through HPA-799. Workers build results; stage/UI objects consume notifications on the Update thread. Do not add a second queue or background work framework.

## Decision C — scores and queries are independent of scan code

- **`SongScoreService`**: Result-stage score save, speed-bucket variant refresh in the published tree, NX score import and post-import refresh. Use `SongScoreStore` for SQLite writes and history lookups; use the library's narrow locked score-mutation operation, not a duplicate library snapshot. Preserve existing score ranking, grade, skill, play count and achievements.
- **`SongQueryService`**: recent plays, bookmark read/toggle, free-text search, genre queries, plus mapping stored chart IDs back to the *current active published* library nodes. Use `SongQueryStore` for database access. Keep the active-roots filter and most recent/ordering semantics.
- **No score-success regression:** a committed `PerformanceSummary` is not reported as saved until the matching in-memory node is refreshed; a failed refresh returns the existing failed status, and an equal/newer concurrent snapshot counts as already current. SQLite `RunId` receipts remain idempotent across retries and speed variants. Preserve per-song/level matching rules for legacy SET.def nodes.

The UI does not need a new state model or protocol. The existing Song Selection, Result and Config call sites simply obtain these services from `IStageGame`.

## Decision D — split persistence by operation, share one context owner

Keep one **`SongDatabase`** infrastructure object responsible only for SQLite path/options, initialization/schema checks, `SongDbContext` creation and ownership. Move business operations from `SongDatabaseService` into three concrete collaborators:

| Collaborator | Responsibility |
| --- | --- |
| `SongCatalogStore` | bulk import, chart/hierarchy queries, active-root chart inventory, cleanup, scan watermarks and rejected-chart metadata |
| `SongScoreStore` | transactional score updates, idempotent save receipts, per-speed score history and top-score reads |
| `SongQueryStore` | recent-play/search/genre/bookmark SQL |

All three receive the **same** context owner/factory and open short-lived DbContexts per operation. Reuse the existing EF queries, transactions and `SongDbContext` schema; move them rather than redesign them. Avoid a generic repository/base-class pattern. Do not retain a second monolithic `SongDatabaseService` that merely delegates to all three stores.

Keep database file path, SQL table/column definitions, chart IDs, score save receipts, bookmark values, and database rebuild/version behavior unchanged. Changing schema or supporting obsolete input formats is out of scope.

## Decision E — production wiring without stage behavioral changes

- **`BaseGame / IStageGame`:** compose and expose one library instance; configure loggers through constructor arguments. Dispose only after stages have stopped accessing it.
- **`StartupStage`:** keep the current phase order, HPA-799 scoped background work, cached-hierarchy-first path, scan fallback, progress text and failure handling. Invoke `SongLibrary`/`Scanner` methods rather than `SongManager.Instance`.
- **`SongSelectionStage`:** use library snapshot/events and `Queries`; keep navigation, filters, prepared-chart selection, latest-only publication reconciliation and active-root filtering intact. The HPA-802 stage split happens **later**, not here.
- **`ConfigStage / SongLibraryReloadService`:** use `Scanner` for reload and `Scores` for NX import, retain the test-injectable delegates and serialized status/activation handling. Reuse HPA-799, not a new task queue.
- **`ResultStage`:** call `Scores` for saving and preserve `ScoreSaveResult` meaning and UI.
- Migrate *all* game and test call sites. No references to the singleton or old monolithic database service may remain after this change.

## Verification, risk and scope boundary

This is a mechanical responsibility move. Do not fold in UI redesign, config schema changes (HPA-803), Song Selection stage splitting (HPA-802), nullable migration (HPA-805), gameplay timing changes, native-specific input work or new assets. No dedicated new art/SFX task is needed.

Risk-ranked regression surfaces:

1. **Startup / scan correctness:** first-run import, warm-cache launch, changed/renamed chart, SET.def/box.def hierarchy, bundled root and empty/unavailable roots.
2. **Concurrency / persistence:** canceled/competing reloads, scan mid-flight edits, recoverable parse errors, score transactions and idempotent retry/refresh.
3. **Stage behavior:** Song Selection tabs/recent/bookmarks, Config reload/NX import, Result save, no cross-activation updates.

The implementation PR must run unit tests plus **MCP-driven out-of-process E2E** on one supported platform. Reuse the existing `Category=E2E` game launch and HPA-797 screenshot tour; extend one focused E2E scenario for missing scan/cache/reload coverage rather than introducing a new test harness. Compare the existing CX Neon/default Song Selection, startup and result screenshots against the baseline at the same 1280×720 virtual resolution; no mockup or visual redesign is planned. Check for missing songs, unexpected boxes, unreadable labels, clipping, or state changes after reload. Screenshots and MCP execution results belong in the **same implementation PR**.

**Review gate:** design-only draft; these are acceptance criteria, not claims of tests already passing.
