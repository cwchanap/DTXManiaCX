# HPA-801 — Song library responsibility split (reviewed design)

**Review addressed:** https://github.com/cwchanap/DTXManiaCX/pull/252#pullrequestreview-6007914307  
**Implementation:** [one-PR plan](../superpowers/plans/2026-11-21-hpa-801-implementation-plan.md)  
**Baseline:** `main` at `5e8b47e311badceafc8942b804a255f0527f9463` (2026-11-21). Re-check code and references against the latest main before changing production.  
**Status:** planning-only draft; no production change or test/E2E execution in this revision.

## Objective and constraints

`SongManager.cs` is ~4,386 lines; `SongDatabaseService.cs` is ~2,385. Together they mix scanning and import, definition parsing, cold/warm hierarchy assembly, published state, SQLite operations, scores and queries. Split them into cohesive concrete objects while **preserving the externally observed library, persistence and gameplay behavior**.

One implementation PR (this draft), maximum three engineer days including test migration and E2E. No DI container, new service interfaces, generic repository hierarchy, event bus, compatibility wrappers, config change, database schema change, new art/SFX, or UI redesign. Reuse `SongLibrarySnapshot`, `SongEnumerationBatch`, `SongListNode`, `SongRootPolicy`, `DTXChartParser`, `NxScoreImporter` and `BundledSongs.AppendTo`. HPA-799's activation-scoped `BackgroundWork.Latest` is the existing stage update-thread boundary.

## Decision 0 — remove confirmed dead surface *before* extraction

Confirm production references on the latest main, then **delete test-only/unused behavior and its dedicated tests**, rather than migrating it to new services. This is a reference-guided deletion, not permission to remove a live code path.

- `SongManager`: `EnumerateSongsOnlyAsync`, `BuildSongListsAsync`, `SaveSongsDBAsync`, `BuildSongListFromDatabasePublicAsync`, `LoadScoreCacheAsync`, `BuildHierarchyFromDatabaseOnceAsync`, public `EnumerateSongsAsync`, `DatabaseExistsAsync`, `GetDatabaseStatsAsync`, `GetDatabaseScoreCountAsync`, `GetTopScoresAsync`, `GetTopScoresForSpeedAsync`, the boolean `UpdateScoreAsync` overload, `FindSongsBySearchAsync`, `GetSongsByGenreAsync`, `DatabaseService` property, `IsEnumerating`, `SetCurrentSearchPaths`, `SongDiscovered` and `EnumerationCompleted`. **Keep `SongLibraryPublished`** and its throwing-subscriber isolation.
- `SongDatabaseService`: unused `SearchSongsAsync`, `GetSongsByGenreAsync`, `GetSongWithChartsAsync`, `GetTopScoresAsync`, boolean `UpdateScoreAsync` overload, and `CleanupStaleChartsAsync`/`CleanupOrphanedSongsAsync`. `AddSongAsync` is a test seeding helper; replace it with test-owned SQLite fixture seeding.
- `SongListNode.PopulateScoresFromDatabase`: delete the DTO→database dependency if no production call remains. Delete stale singleton references in docs.
- `_pendingSearchPaths` duplicates published `_currentSearchPaths` except through the test-only setter/dead DB-build wrapper; retain **one** published active-root array. Do not change the accepted-root validation or publication contract.

Free-text search and genre queries are **not** acceptance requirements: present code-search references are production definitions and test-only calls. Preserve **live** recent plays and bookmarks. If a suspected dead symbol has a production caller, keep its behavior and document why.

## Decision A — non-null game-lifetime composition, singleton gone first

`BaseGame` constructs a non-null `SongDatabase(AppPaths.GetSongsDatabasePath())` and `SongLibrary(database, logger, ...)` before any stage consumes it, exposes a concrete `SongLibrary` on `IStageGame`, and disposes it **after** stages. `SongDatabase` owns path/options, SQLite initialization/schema/version handling and context creation; `CreateContext` rejects use before `InitializeAsync`. Startup calls initialization without supplying a DB path. Remove `StartupStage.GetSongsDatabasePath` and the late nullable database assignment/nullable snapshots; tests inject `SongDatabase` pointing at their own temporary SQLite database.

**First structural move:** rename `SongManager` to `SongLibrary` and rewire all production/test construction to the game-owned instance; delete `Instance`, `ResetInstanceForTesting`, `Clear()` and the singleton test collection. Make this first so later extractions do not need a temporary forwarding facade or a second fixture rewrite. Preserve explicit logger injection; no static service locator. Use the final constructor/seam pattern in migrated tests.

## Decision B — `SongLibrary` owns the entire scan transaction and publication

**One owner:** move `EnumerateAndImportSongsCoreAsync`, `TryBeginEnumeration` and `EndEnumeration` into `SongLibrary` (rename the public operation `ScanAndPublishAsync` if useful). **The single-flight slot wraps batch build, SQLite bulk import, finalization, publication, and the post-publication metadata/watermark work, and is released only in `finally`.** `SongLibrary` also owns the published-state lock, root/version/count snapshot, event and locked score-node mutations. No other object may publish part of the shared tree or release the slot early.

Preserve these contracts (existing `SongManager.cs:679–835, 1510–1610`):

1. An overlapping scan throws `SongEnumerationBusyException`, including during cancellation wind-down. Canceled/incomplete/failed scans do not publish a partial hierarchy; post-commit finalize/publish exceptions retain their distinct `SongEnumerationPostCommitException` result.
2. Scan → import DB (transaction committed) → finalize pending nodes → atomically publish complete hierarchy → report/watermark, in that order. Keep existing successful/failed event isolation; callbacks run outside the published-state lock.
3. Scan-start watermark and five-second backoff, per-root recoverable-error dirty status, rejected-tab counts, active-root chart counts, and inactive-root retained rows stay intact.
4. An explicit accepted empty root set publishes a coherent empty snapshot. A failed/unavailable root does not erase the valid prior snapshot. Published `SongLibrarySnapshot` is versioned, coherent, and safe for stage readers.
5. Use `BundledSongs.AppendTo` once and retain bundled-root top-level merging and multiple configured-root BOX headers.
6. `SongSelectionStage` keeps HPA-799's latest-only activation-scoped subscription and update-thread reconciliation, with no new worker→UI queue.

`SongLibraryScanner` is **stateless** with respect to publication/single-flight: it builds a `SongEnumerationBatch` and provides `NeedsEnumerationAsync(activeRoots)` / file-inventory helpers using injected I/O delegates. It cannot own the scan task lock or the published hierarchy.

### Moved-file check

Pass the already canonical `activeRoots` into moved-file lookup (`FindMovedFileAsync`), rather than reading `SongLibrary._currentSearchPaths` or falling back to hard-coded default roots before publication. **This is one deliberate narrow behavior fix:** look for a moved chart in the user's configured active roots. Retain the existing filename heuristic and rescan trigger; do not delete move handling or rewrite persistence. Add a regression test with a chart moved between configured folders and ensure the scan still runs. This removes scanner→library state dependency.

## Decision C — reader and hierarchy, without rewriting the cold path

- `SongDefinitionReader` handles SET.def and box.def decoding/line reconstruction, encoding fallback, metadata, color and label parsing (no DB/publication state).
- **Cold start keeps building the tree during traversal** and puts root nodes/pending songs in the existing batch. Do **not** flatten/rebuild cold trees.
- `SongHierarchyBuilder` owns the existing **warm-start DB reconstruction** plus pending-node finalization. Share **one** helper/factory for BOX nodes and configured-root headers across cold and warm paths (title, genre, skin, text color, root marker, breadcrumbs); avoid a new factory framework or duplicate implementations.
- Extend existing `BuildSongListFromDatabase_ShouldMatchTheEnumeratedHierarchy` to compare cold and warm hierarchies including `SkinPath`, text colors, multiple configured roots, bundled-root placement, ordering and difficulty labels. Parity is a deterministic unit-test gate, not a screenshot substitute.

## Decision D — persistence, score, query and ownership table

| Concrete type | Owns | Constructed by |
| --- | --- | --- |
| `SongDatabase` | Non-null path/context options, `InitializeAsync`, schema checks, `CreateContext` | `BaseGame` (test injects temp SQLite DB) |
| `SongCatalogStore` | Bulk import/cleanup, active-chart queries, per-root scan metadata/watermarks/rejected counts | `SongLibrary`; receives `SongDatabase` |
| `SongScoreStore` | Transactional score save, `RunId` receipts/race resolution, history and speed buckets | `SongLibrary`; receives `SongDatabase` |
| `SongDefinitionReader` | SET.def/box.def parsing and file-read seam | `SongLibrary` / scanner |
| `SongHierarchyBuilder` | Warm-start hierarchy and pending-node finalization; shared BOX/root-node factory | `SongLibrary` |
| `SongLibraryScanner` | Stateless filesystem traversal, freshness and batch building; injected file I/O | `SongLibrary` |
| `SongLibrary` | Published hierarchy/version/lock, single-flight scan transaction and publication, locked score refresh; exposes `Scanner`/`Scores`/`Queries` | `BaseGame` |
| `SongScoreService` | Persist Result summary **then** refresh the matching in-memory variant; NX score import | `SongLibrary` |
| `SongQueryService` | Recent plays, bookmark read/toggle and their SQL, mapping against current active nodes | `SongLibrary`; receives `SongDatabase` |

**No `SongQueryStore`:** the remaining live SQL query surface is small; keep it directly in `SongQueryService`. Do not preserve unused search/genre methods. The two real stores share one `SongDatabase` and short-lived `SongDbContext` instances; retain EF query shape, transaction boundaries, schema version, song/chart IDs and score receipt rules. Do not make a monolithic `SongDatabaseService` forwarding façade.

**Score save invariant:** Result must not report "saved" until the committed `PerformanceSummary` has refreshed the matching active chart/instrument/speed variant. Concurrent fresher published score = success, no matching node/DB-read failure = existing failed presentation, retry = idempotent via `RunId`. Preserve active-root filtering and recency ordering, bookmarks, NX import and speed-bucket performance history.

## Decision E — explicit migration of test seams

Keep behavioral fault-injection coverage. Move mutable production test hooks to optional **constructor** delegates; production defaults use the extracted concrete behavior.

| Existing test seam | New owner / injection | Must retain |
| --- | --- | --- |
| `ParseSongEntitiesCoreAsync`; `EnumerateFilesCore`; `EnumerateDirectoriesCore` | `SongLibraryScanner` constructor I/O funcs | parse failures, directory exceptions, discovered chart lists |
| `ReadAllLinesCoreAsync` | `SongDefinitionReader` constructor file-read func | fallback decoding and unreadable definitions |
| `BuildEnumerationBatchCoreAsync` | `SongLibrary` constructor build-batch func | incomplete-batch rejection/cancellation |
| `ImportSongsCoreAsync` | `SongLibrary` constructor import func | busy state, blocked imports, cancellation and database-failure paths |
| `FinalizePendingNodesCore` | `SongLibrary` constructor finalize func | post-commit finalization failure |
| `PublishEnumerationCore` | `SongLibrary` constructor publish func | post-commit publication failure |

When all extractions finish, the default delegates point to the new collaborators; prefer minimal constructor arguments rather than test-only interfaces or a service container. **Migrate, do not retire** existing meaningful tests for busy/cancel slot, incomplete batch, post-commit errors, watermark and coherent publication. Retire only tests of explicitly deleted unused methods and redundant private implementation details.

Drop `GetDatabaseStatsCoreAsync` and the four old test-only `SongDatabaseService` constructors; use ordinary temporary real SQLite databases (no new persistence mock layer). Tests use the constructed library/store directly, not `GetUninitializedObject` or static resets.

## Stage wiring and automated acceptance

- `StartupStage`: preserve stage phase order, progress, cold/warm cache behavior and HPA-799 worker/apply sequence. `SongSelectionStage`: subscribe to library snapshots; keep All/Recent/Bookmarks, prepared chart, filtering and active-root reconciliation. HPA-802's stage split is out of scope.
- `ConfigStage` / `SongLibraryReloadService`: scanner for reload, score service for NX import, preserve activation/cancellation behavior. `ResultStage`: use score service with existing save result semantics. `IStageGame` exposes exactly one game-owned library.
- Delete all remaining old `SongManager`/`SongDatabaseService` symbols after migration, not aliases. Keep full canonical unit suite green after each extraction.

**End-to-end requirement:** use the existing `gameplay-e2e-windows` GitHub Actions job, exercised/inspected **via MCP**, as the primary real-process E2E. `GameplayAutoPlaySmokeTests.GameplaySmoke_ShouldPersistIndependentSpeedBucketsAndReuseBucketAcrossPitches` already runs three game launches over one songs.db, covers cold/warm replay and Result persistence; the HPA-797 seven-image screenshot tour covers Title, Config, Song Selection, Lanes, Tab and Result. Reuse existing recent/bookmark/reload unit/integration tests; **do not build a second E2E harness or extend it unless a genuine untested critical regression is found**.

**Visual acceptance is still required:** through MCP fetch the job's screenshot artifact and visually inspect the existing Song Selection, gameplay and Result screens against current-main baseline (screenshot viewing or automated diff). PNG-integrity CI alone is insufficient for layout/data parity. No mockup or new artwork. **The job currently skips draft PRs**; evaluate it when the implementation PR is ready for review (or run an existing supported CI dispatch), not as a claim about this docs-only draft. One Windows platform is sufficient; no native-device acceptance required.

These acceptance checks are automated/agent-executed, not a human approval gate. The implementation PR must link CI outcome, MCP observations, screenshot evidence and any expected baseline differences. No production tests or screenshot checks have been run as part of this plan revision.
