# HPA-795 — Remove dead code and migration-era infrastructure (design)

**Linear:** https://linear.app/cwchanap/issue/HPA-795/cleanup-delete-dead-code-legacy-shims-the-startup-tracer-and-db  
**Status:** Proposed; design-only until approved.  
**Delivery:** One implementation PR (this draft PR), <=3 engineer days.  
**Dependencies:** None. Unblocks HPA-796 and HPA-797.

## Outcome

Reduce the code that future CX refactors must move without changing the player-visible behavior. Remove unused UI types and app-version compatibility shims, delete the HPA-192 startup profiler, and replace the song database's additive migration code with one schema version. There are no real users to migrate, so a **song database reset on version mismatch is intentional**.

This is deletion and consolidation, **not** a rewrite of the startup pipeline or database architecture.

## Verified current seams

- **Startup instrumentation:** DTXMania.Game/Program.cs creates StartupTimingTrace, Game1 hosts StartupCriticalPathTrace, and startup timing/observer plumbing passes through StartupStage, TitleStage, BaseStage, StageManager, SongManager and SongDatabaseService. Supporting code lives in Lib/Stage/StartupCriticalPathTrace.cs, StartupCriticalPathHost.cs, StartupTimingTrace.cs and Lib/Song/StartupSongLoadTimingObserver.cs. HPA192_CRITICAL_PATH and HPA192_EXIT_AFTER_CRITICAL_PATH are diagnostic-only switches. tools/hpa192 and tracer-specific tests exist.
- **Crash diagnostics are distinct:** CrashReportRuntime and CrashContextPublisher provide managed crash capture and startup milestones. These must survive profiler removal. The Game API main-thread queue and screenshot support also survive.
- **Song database:** Lib/Song/Entities/SongDatabaseService.cs currently uses __DatabaseVersion as a Unicode-support marker, calls EnsureCreated, applies SQLite PRAGMAs, then runs additive column/table migrations. Lib/Song/Entities/SongDbContext.cs defines the EF schema. The __EnumerationMetadata table is separate raw-SQL runtime metadata used by library freshness and must still be created for a new database.
- **Compatibility shims:** Lib/UI/Components/UIButton.cs, UIList.cs, UIImage.cs are only referenced by their own tests; Lib/UI/Layout/PerformanceUILayout.cs contains unused legacy layout aliases. Lib/Song/Entities/SongChart.cs and SongScore.cs contain compatibility properties. PerformanceStage has an older-caller initialization path, and SongManager has a parse-only reflection-test helper. ConfigData.DTXPath mirrors SongRoots[0], while Config.ini consumers and E2E fixtures still use the DTXPath input key.
- **Build baseline:** Current CI builds Windows and macOS game variants and runs DTXMania.Test, Automation.Tests and VideoRecorder.Tests; the Windows E2E suite also exercises an actual game process. Follow the repository's current SDK and project files rather than old design documents.

## Decisions

### A. Delete only migration-era application compatibility

1. First search all production references and identify each symbol's **real owner**. Remove test-only UI components, unused legacy layout groups/aliases, SongChart/SongScore shim properties, rank-ordinal normalization for old persisted data, the old-caller performance initialization fallback and the SongManager parse-only reflection hook *if* no production call site requires them.
2. Remove or update tests whose sole assertion is compatibility with those deleted symbols. **Do not** remove behavioral tests of equivalent current features; test through the current public/internal interfaces.
3. Make ConfigData.SongRoots the sole in-memory song-folder source. Remove the DTXPath mirror and its synchronization. **Keep Config.ini import**, including the legacy DTXPath **input key**, by mapping that key directly to the first SongRoots entry when appropriate; keep indexed SongRoot.N precedence. Preserve existing E2E and recorder fixture compatibility.
4. Preserve DTX/NX **file-format compatibility**: SET.def handling, Japanese encodings, NX score.ini import, chart parsing, music XML/GP import and supported DTX formats are not obsolete app-version shims.
5. Do not mechanically delete every occurrence of the words “legacy” or “compat”; audit and retain genuine game/data-format behavior.

### B. Remove the full startup timing/critical-path instrumentation

- Delete StartupCriticalPathTrace, StartupCriticalPathHost, StartupTimingTrace and StartupSongLoadTimingObserver; remove diagnostic interfaces, observer overloads, startup-timing fields, spans and HPA192-specific environment variables/exit paths from Game1, Program, stages, SongManager and SongDatabaseService.
- Remove tools/hpa192 and tests dedicated only to the removed profiler. Adjust tests/fakes that depend on observer-aware signatures or tracing constructors.
- Preserve the normal startup state transitions, existing song enumeration/cancellation, Game API health/screenshots and **all** crash-reporting breadcrumbs/startup milestone publication.
- No replacement instrumentation framework. Zero timing lines is acceptable; if keeping one total startup duration log is trivial with the existing ILogger, it must not revive event spans, custom clocks or profiler state.

### C. One song database schema version, no migrations

Use SQLite's built-in **PRAGMA user_version** as a single integer version marker (initial value: **1** for this new policy). Do not create another metadata table or use EF migrations.

**File-backed initialization contract:**

1. Under the existing initialization lock/semaphore, if the songs.db file exists, probe SQLite validity and read user_version *before* opening a long-lived EF context or calling EnsureCreated.
2. If invalid or user_version differs from CurrentSongSchemaVersion (including 0, which denotes databases created before this policy), close/clear SQLite connection pools, remove the **song database only**, then create it anew. Resetting saved local scores, history and bookmarks is accepted and should be mentioned in the PR description. A file deletion failure must surface an initialization error, not silently pretend success.
3. On a new file, create the current EF schema with EnsureCreated, apply the existing journal_mode / case_sensitive_like PRAGMAs, and initialize __EnumerationMetadata (which is not part of SongDbContext). Only **after these steps succeed**, store CurrentSongSchemaVersion in user_version and mark the service initialized.
4. On a valid, matching-version database, keep persisted songs/scores/bookmarks unchanged. Reopening is not a reason to rebuild or rewrite the schema.
5. Remove __DatabaseVersion/UnicodeCollation as a pseudo-version check and all Ensure*Column/score-scope/receipt migration paths. **Keep** all current EF model fields, score-save receipts and enumeration metadata *runtime functionality*. New schema fields in future require a deliberate version bump and recreation, not an ALTER pipeline.
6. Keep functional Unicode handling: SQLite UTF-8 text and Japanese filenames/titles must continue to work. The old __DatabaseVersion marker never proved actual encoding; verify with round-trip tests instead.
7. Test-only/in-memory SongDatabaseService constructors already accept pre-created contexts. Keep that test seam without requiring a file-level PRAGMA version check.

**Important:** The separate configuration SQLite store and its Config.ini import lifecycle are **out of scope**. Never delete the config database when replacing songs.db.

### D. Explicit non-goals

No new dependency injection framework, event bus, migration engine, generalized compatibility checker, schema migration recovery mechanism, telemetry, benchmark, visual change, input-stack consolidation or test-suite reorganization. HPA-796/797/798/804 own their respective refactors. Do not remove historical docs merely because they mention the deleted profiler; HPA-798 separately owns stale docs cleanup.

## Acceptance contracts

- Windows and macOS projects compile; their existing unit suites and affected startup/song-library E2E smoke tests pass.
- No runtime use of StartupTimingTrace, StartupCriticalPathTrace, IStartupSongLoadTimingObserver, HPA192_* diagnostics or tools/hpa192 remains. Crash report creation, Game API, startup and game transitions still work.
- A fresh songs.db gets the current marker and all required tables, including __EnumerationMetadata; Japanese song title/file metadata persists and reloads.
- A same-version restart keeps saved scores/bookmarks; a mismatched-version database is replaced and repopulated by normal scanning; a failed reset does not report success.
- SongRoots, indexed config loading and the Config.ini DTXPath input alias still select the right folder. The Config SQLite file is unaffected.
- All removed types/helpers have no live production references; delete their obsolete tests but preserve tests proving surviving game behavior.
- No user-visible change to gameplay, media, file compatibility or score calculation beyond the explicitly accepted song DB reset on version mismatch.
