# HPA-803 — Declarative settings and SQLite-only configuration

**Linear:** https://linear.app/cwchanap/issue/HPA-803  
**Implementation:** [one-PR plan](../superpowers/plans/2026-11-27-hpa-803-implementation-plan.md)  
**Baseline:** main `e7204eba135e0b1b201135e2a5027b6d94fa0539` (2026-11-27). HPA-797 and HPA-802 are Done; no open PR competes.  
**Status:** design only; no implementation, builds, test runs or visual checks performed.

## Objective and boundaries

Make a new ordinary persisted setting a single declaration, not edits in the data model, parser, save dictionary, setter and ConfigStage. Retain the existing typed game-facing ConfigData API and the two-pane Config UI. Eliminate Config.ini bootstrap/import end to end, including recorder and test fixtures. Use the current .NET 10 SDK, MonoGame, SQLite, unified test project and existing MCP. One PR, maximum three engineer days. No new settings, assets, settings editor, source generator, DI framework, settings event bus, input redesign (HPA-804), nullable sweep (HPA-805), ORM change or new database schema. No compatibility migrations for obsolete INI/DB keys. Existing canonical keys and supported values remain because changing them yields no benefit; no extra alias or migration logic.

## Design

### Single declaration, cached metadata table

Use an internal, narrowly scoped property annotation (e.g. ConfigSettingAttribute) on each **live persisted scalar** in ConfigData. Its property name is the canonical database key (all current canonical scalar keys already match); CLR property type and initializer provide the type/default. The annotation supplies optional Config category, explicit stable order, label, description, UI bounds/step, and only the applicable normalization/formatting policy. Hidden entries have no editor metadata. Example (illustrative): `[ConfigSetting(Category = Drums, Order = 60, Label = "Metronome", Description = "...")] public bool Metronome { get; set; } = false;`. A simple bool needs only this declaration; no registry registration, key literal, UI branch or named manager setter. Default is initialized exactly once by normal ConfigData construction; if metadata needs the default, read it from a fresh default ConfigData (never cache AppPaths defaults across app-data roots).

Build a small internal SettingsCatalog once from annotated public read/write properties. It exposes ordered immutable descriptors and lookup by ordinal key, validates unique keys/order within each category, supported CLR types (bool, int, string, named enums), valid bounds/step and complete UI metadata. Cache metadata/accessors; discovery is not on the render or gameplay hot path. Retain normal typed property reads in gameplay; no reflection or dictionary reads there. Use simple reflection for persistence and control construction/editing; compiled expressions, generic frameworks and attribute scanning beyond ConfigData are unnecessary. Keep defaults in property initializers; do not build a second defaults dictionary. For range and enum formatting, reuse existing ScrollSpeedRange, PlaySpeedRange, PitchRange, RiskyRange, enum label tables and narrow explicit policies referenced by the declaration. A new ordinary toggle or bounded int uses the built-in descriptor behavior, not another switch arm. Separate UI range from persisted normalization where current behavior differs (audio latency UI 0–500 step 10, persisted/programmatic value nonnegative; screen dimensions and API port have no new clamp). Invalid stored scalar values leave defaults/current values as the existing load policy requires; preserve named-enum-only parsing, invariant number formatting, current accepted bool spellings, and string non-null persistence. Canonical enum names are persisted, UI labels remain separate. Keep existing enum fallback on invalid programmatic values. Preserve existing normalization-on-save of play speed/pitch/risky even for direct property writes; use shared policy, not a save-only duplicate.

### Ownership

| Owner | Responsibilities |
| --- | --- |
| ConfigData + SettingsCatalog | Typed values, defaults, scalar metadata, codec/normalization and editor description |
| ConfigManager | Load/save lifecycle, generic scalar mutation with change detection/dirty tracking/notification, existing collection handling, path normalization, API-key provisioning |
| ConfigStage | Build existing widgets from visible ordered descriptors, compose special controls, navigation, live side effects and render |
| ConfigDbSchema + SqliteConfigStore | SQLite schema and transactional storage only; shared with recorder through linked sources, not game dependency |
| E2E/Recorder | Explicit per-run seed rows and runtime ownership; no duplicated game metadata registry |

Annotate all canonical persisted scalars (version, skin fields, display dimensions/fullscreen/vsync, gameplay modifiers and toggles/enums, audio latency, API enable/port/key). Do not invent persisted volume behavior or expose secrets/API settings in UI. Leave unused sound volume fields unannotated with explanation; no volume feature. Keep dynamic collections out of scalar catalog: ordered SongRoot.N, Key.*, explicit unbound markers, SystemKey.*, MidiVelocity.N, sparse AutoPlay.N. Preserve their existing validation, precedence, duplicate/conflict handling, ordering, mutation and persistence. Preserve canonical SongRoot.N defaults, active path validation/correction and skin Default token relocation; remove only old DTXPath migration, RandomFromSubBox alias and bare AutoPlay compatibility warning/branch, plus any other verified obsolete config-row migrations. Never delete legitimate NX score import or skin metadata INI/Theme.ini support.

### Persistence and mutation

Load canonical scalar rows through the catalog; route dynamic keys through current dedicated parsing. Keep the established invalid existing DB failure and load-before-save guards. Missing DB always creates current defaults and normalized managed paths; no INI read, import, deletion or fallback, even if a stale INI exists. Existing canonical v1 DB loads without a migration; do not bump schema merely for this change. Unknown/obsolete keys ignored and not emitted by the next complete snapshot. Preserve path correction persistence/retry, API key generation on enabled + empty key (persist before use; rollback on write failure), deferred save, subscriber isolation and retry on failed flush. Keep existing reset semantics and startup/read failures; don't introduce saves on a raw property write or on load of an unchanged valid DB. Reset must use fresh defaults and existing notifications. Ensure repeated loads and current notification semantics remain intentional and test-covered rather than changing them incidentally.

Provide one generic scalar mutation entry point on IConfigManager/ConfigManager (e.g. SetScalar<T>(canonical key, T value)); validate descriptor/type, normalize, compare actual old/new values, update typed property, mark dirty where applicable, then dispatch existing change notifications. Existing named setters actually used by other game code can delegate to it (e.g. SetScrollSpeed/AdjustScrollSpeed); remove unused forwarding methods if tests/callers can migrate in scope. Direct property assignment is still in-memory only. No new generic subscription API absent a consumer: the common dispatch preserves ScrollSpeedChanged with old/new and per-subscriber isolation on UI and runtime edits, as well as existing load/reset transitions without marking dirty merely for loading. Compound resolution and path setters retain their existing semantics; use shared scalar metadata where appropriate but do not split a compound edit into independent observable transactions. Collection events remain distinct. Existing UI BaseConfigItem.ValueChanged behavior remains separate from manager notifications.

### Config screen

Use existing ToggleConfigItem, IntegerConfigItem, DropdownConfigItem and descriptions; construct scalar controls from descriptor metadata and bind to the current manager.Config at invocation time (reset can replace ConfigData). Use the shared manager mutation API, not direct property setters. Category and ordering are explicit, with gaps for existing special controls. Retain stage-local special UI for combined resolution, dynamic skin selector and immediate reload, song-folder panel, key mapping, NX score import, and AutoPlay all/per-lane controls (including Mixed text and lane ordering). FFmpeg availability is a stage-only edit guard and warning overlay for speed/pitch; metadata owns their normal label/range/format and base description. Do not embed graphics/runtime dependencies in persistence. Preserve System and Drums category labels, descriptions, order, selection/focus, displayed values, clipping/scroll, navigation and skin/theme behavior; Exit remains unchanged. No visual redesign.

### DB-only automation

Use the existing SqliteConfigStore writer and ConfigDbSchema across the game and E2E; link the same writer source in the recorder (already links schema), keep recorder independent of game/MonoGame. No copy of the live DB file, WAL or SHM. SourceConfigDatabase reads source read-only with existing schema/path validation. RecordingSandbox creates an isolated app-data config.db from source logical rows plus existing owned overrides: generated API key/port, API enable, all ten AutoPlay lanes, NoFail, fixed resolution/windowed and other current owned values. Preserve unowned canonical rows and input/skin/root settings. Remove INI serialization, INI-only escaping/trimming guards, and obsolete bridge-only tests; retain path validity/absolute requirements and actual game normalization semantics. Use parameterized SQLite rows, close/dispose writer before launch (disable pooling for transient store connections as needed for Windows cleanup); never write source. Preserve existing success cleanup and failed-run evidence/ownership behavior; don't redesign recorder lifecycle.

E2EFixtureBuilder seeds config.db before launch with canonical SongRoot.0, SkinPath, SystemSkinRoot, display, gameplay and API rows. Omit AutoPlay.N for manual fixture. Drop LegacyConfigPath from E2EFixture/E2ERunPaths and explicit constructor seam, update all call sites. Replace INI fixture/artifact text with a prelaunch snapshot of synthetic seed rows (before game mutation), and keep durable-state assertions reading actual DB after shutdown. Don't copy a live SQLite database or expose real recorder API keys in artifacts. Keep a true no-DB first-launch test separate from preseeded fixtures so default creation remains covered. Search active scripts, docs, tests and workflows for stale Config.ini references, including AGENTS/CLAUDE, MCP/README, tools/README, benchmark recipes and recorder runbooks; update live instructions only, leave historical NX/evidence docs intact. Cloud UAT recipes must seed the same v1 schema and canonical rows; document runnable SQL using parameterized seeding or correctly quoted paths, not a legacy INI. No actual generated artifacts committed.
